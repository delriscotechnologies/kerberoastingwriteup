Kerberoasting

A routine Kerberos request can become the starting point for recovering a service account’s password. This Active Directory lab follows that path, using Rubeus to extract service-ticket material and Hashcat and John the Ripper to test password candidates offline. The aim is to understand why weak credentials remain exposed and what recovering them can allow.

Attack path

Let’s start with the basics. A Service Principal Name identifies a service instance and associates it with the Active Directory account running that service. Kerberos uses this association when issuing a service ticket.

An authenticated domain user with a valid ticket-granting ticket can request a service ticket without knowing the service account’s password. Part of the returned ticket is encrypted with a key derived from that password. With RC4, the encryption used in this lab, the account’s password hash provides that key. RC4 is a legacy encryption type that can still be explicitly allowed for compatibility with older services.

Because each password candidate produces a key we can test against the ticket material, we can check guesses offline without sending each guess to the domain controller. Recovering the password can allow us to authenticate as the service account and access resources permitted by its rights. Control of a domain controller or the wider domain would depend on that account having sufficient privileges.

Using Rubeus, we can perform Kerberoasting to request these service tickets and export their encrypted material. Password-cracking tools such as Hashcat and John the Ripper then derive a key from each candidate and check it against that material. A successful match identifies the service account’s password. RC4 makes candidate testing relatively fast; weak or predictable passwords can shorten the search further.

Using Rubeus

The service accounts in this lab explicitly permit RC4. Rubeus may return AES material in other environments.

Assuming we already have an authenticated Active Directory session and can reach the domain controller, we use the following command to find user accounts with registered SPNs, request their service tickets, and save the extracted material to spn.txt:

PS C:\Users\Jaime\Downloads> .\Rubeus.exe kerberoast /outfile:spn.txt

The kerberoast action handles the service-ticket requests. /outfile:spn.txt writes records containing the encrypted ticket material and identifiers such as the account and SPN, in a format suitable for offline password testing. spn.txt is the output filename; its contents are more than a list of SPNs.

Testing password candidates offline

With the exported material in spn.txt, the next step is offline password cracking. We can use Hashcat with rockyou.txt, a wordlist provided by Kali’s wordlists package. Each line contains a password to try; the commands below assume an extracted copy of the list is in the working directory.

(kali㉿kali)-[~]
└─$ hashcat -m 13100 -a 0 spn.txt rockyou.txt --outfile="crack.txt"

-m 13100 selects Kerberos service-ticket material using RC4, and -a 0 selects a wordlist attack. Hashcat tries each password in rockyou.txt against the ticket material and saves recovered hash-and-password pairs to crack.txt.

If a warning stops the run, --force can bypass certain warnings. Review the cause first; Hashcat discourages routine use. It does not repair an invalid hash or an incorrect mode.

Recovery result

Recovery can take time. It depends on the password candidates, the ticket’s encryption type, and the hardware available. A wordlist only recovers a password if it contains a matching candidate.

Using John the Ripper

I prefer John the Ripper because it feels faster in my workflow. Actual performance depends on the hardware, format, and candidates being tested.

(kali㉿kali)-[~]
└─$ sudo john spn.txt --fork=4 --format=krb5tgs --wordlist=rockyou.txt --pot=results.pot

John tries passwords from the same rockyou.txt against spn.txt. --format=krb5tgs selects Kerberos service-ticket material using RC4, --fork=4 starts four processes, and --pot=results.pot stores recovered results. This requires a John the Ripper Jumbo build with that format available.

The example loads three RC4 service-ticket entries and starts four processes. The two highlighted lines show entries matching the same password, Barranquilla123.

This example shows how weak service-account passwords can expose an Active Directory environment to offline credential recovery, especially when legacy RC4 is still used. Predictable or reused passwords and poorly managed service accounts increase the risk of credential compromise. The impact follows the account’s permissions and can include lateral movement or privilege escalation.

How to reduce the risk

Strong credentials

In July 2025, NIST published password guidance. For user passwords:

  • Use at least 15 characters when signing in with a password alone.
  • Block common or leaked passwords.
  • Favor length over rules requiring a capital letter, number, or symbol.
  • Change compromised passwords, rather than changing them on a fixed schedule.

For added protection:

  • For service accounts you manage yourself, use at least 30 random characters. Use a different password for each account and save it in an approved password manager.
  • Use FIDO2 security keys for user and administrator sign-ins where supported. They do not replace service-account passwords.

Managed accounts

Use a group Managed Service Account (gMSA) if your application supports it. Windows creates the password and changes it automatically every 30 days by default. Allow only the servers running that service to retrieve it.

Modern encryption

Keep domain controllers updated and configure service accounts and applications to use AES. After checking compatibility, disable obsolete RC4 and DES. If an old account lacks AES keys, plan a password reset with the service owner. AES makes offline guessing more expensive; weak passwords can still be recovered.

Least privilege

Give each service account only the permissions its service needs. Avoid privileged group membership and avoid using administrative identities to run ordinary services.

These controls make recovery harder, but do not guarantee time to detect an attack. Offline guesses do not produce domain login events. Monitor suspicious ticket requests and service-account activity, and investigate signs of misuse.

Final takeaway

Modern Kerberos encryption increases the cost of offline password testing, but predictable passwords remain a weakness. AI-assisted guessing adds to that challenge: models can learn human patterns and use available personal details or previous passwords to generate more targeted guesses. Each guess still has to be checked against the encrypted ticket material. The practical risk is that weak or reused passwords can remain recoverable even when AES is used. As these techniques improve, defenses need to keep pace through random secrets, modern encryption, restricted permissions, and monitoring of account activity.
